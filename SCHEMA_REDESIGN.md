# RadServe — Schema Redesign (Phase 1)

Status: **APPROVED 2026-08-17.** Review decisions:

1. Equipment type list confirmed.
2. Request channels confirmed (Phone, Email, WhatsApp, Walk-in, Other).
3. `service_requests.equipment_id` stays NULLABLE for flexibility during
   testing/early use; revisit tightening to NOT NULL once workflows settle.
4. Single currency INR. Amounts stay NUMERIC(12,2) (Postgres `money` type is
   discouraged — locale-bound formatting). A `currency_code CHAR(3) DEFAULT 'INR'`
   column is added to work_orders and parts_inventory for future-proofing;
   UI formats as ₹.
5. Vendor-import columns are deferred (not deleted conceptually): DDL preserved
   in a comment block in the migration; a proper `installed_base` table can be
   added later if the vendor feed becomes a requirement.

Target workflow (agreed):

```
CUSTOMER
   │
   └──< EQUIPMENT
          │
          └──< SERVICE REQUEST        (staff log these on behalf of customers)
                    │
                    └──< WORK ORDER   (also created directly by PM schedules)
                           │
                           ├──< TECHNICIAN ASSIGNMENT
                           │
                           └──< PARTS USED
                                      │
                                      └── PARTS INVENTORY
```

## Design decisions (apply everywhere)

1. **UUID primary keys + human-readable codes.** Every table gets a UUID PK
   (`gen_random_uuid()`) and, where humans reference records, a unique code
   (`CUST-0001`, `SR-2026-0001`, `WO-2026-0001`) generated by a sequence-backed
   function — no more `WO-${Date.now()}` in app code. Fixes the current
   bigint/uuid inconsistency.
2. **CHECK constraints on every status/enum field.** The app's dropdowns and
   the database agree by construction. CHECKs, not Postgres enums — easier to
   extend later (`ALTER TABLE ... DROP/ADD CONSTRAINT` vs enum surgery).
3. **All people-references are foreign keys**, never name strings.
   Users (`auth.users`) for who *did* something; `technicians` for who is
   *assigned* to field work. A technician row can optionally link to a login.
4. **Database-maintained metadata.** `created_at`/`updated_at` on every table,
   with a trigger maintaining `updated_at`. App code never writes these.
5. **Working audit trail.** A generic trigger writes INSERT/UPDATE/DELETE with
   old/new JSONB to `audit.activity_log` on every business table. (Function
   exists today; it is attached to nothing.)
6. **Sane text lengths.** Codes VARCHAR(30), names/labels VARCHAR(255),
   free text TEXT. Nothing under 30 characters anywhere.

## RLS policy mapping (same model as migration 006)

| Tables | SELECT | INSERT/UPDATE | DELETE |
|---|---|---|---|
| customers, locations, manufacturers, equipment, technicians, parts_inventory | any authenticated role | admin | admin |
| service_requests, work_orders, workorder_technicians, workorder_parts, maintenance_schedules, qc_tests | any authenticated role | admin + technician | admin |
| user_profiles | own row; admin all | own row (role column locked) | admin |
| audit.activity_log | own rows; admin all | trigger only | nobody |

One deliberate change from today: **parts_inventory moves from admin-write to
admin-write for master fields, but stock movements happen via workorder_parts**,
which technicians can write. Technicians consume stock by recording usage — they
don't edit the catalog.

## What this fixes (traceability to findings)

| Finding | Fix |
|---|---|
| Undersized varchars | All import columns dropped; nothing under VARCHAR(30) |
| No CHECK constraints | Every status/enum field constrained |
| No service request entity | Table 5 |
| No parts-used record; stock never moves | Tables 8 + triggers |
| Technician as name string | Table 7 with real FKs |

| Empty audit trail | Trigger attached everywhere |
| Dead trigger functions | Rewritten and attached |
| Orphan columns | Dropped |
| WO-${Date.now()} numbering | Sequence-backed generators |
| labor/parts/total cost drift | Generated columns + trigger rollup |

## Open questions for your review

1. **Equipment types** — is the CHECK list right for your dealership
   (X-Ray, CT, MRI, Ultrasound, Mammography, Fluoroscopy, PET, SPECT, DR/CR, C-Arm, Other)?
2. **Request channels** — Phone, Email, WhatsApp, Walk-in, Other: anything else?
3. **Should a service request require a registered equipment?** Currently
   nullable (attach during triage). Making it NOT NULL is stricter but means the
   machine must be registered before a request can be logged.
4. **Currency** — costs are plain NUMERIC. Single currency (INR?) assumed. OK?
5. **The vendor-import columns** — confirm parking them is acceptable, i.e. no
   current report depends on division/service-partner/warranty-feed fields.
